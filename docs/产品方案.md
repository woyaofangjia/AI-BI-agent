# 销售数据智能查询 Agent · 一页纸产品方案

> 一句话：让运营、销售、管理层用一句中文直接"问数"，替代"提需求 → 等排期 → 写 SQL → 出报表"的传统取数流程。
>
> 界面演示见 [docs/images](images)，实测数据见 [docs/测试记录.md](测试记录.md)

## 1. 背景与问题

- 业务方查销售数据依赖 SQL / BI 工具：**门槛高**（非技术同学写不了 SQL）、**响应慢**（临时取数要等数据同学排期）。
- 一次"上个月 TikTok 卖了多少"的临时问题，从提需求到拿到数字通常以小时甚至天计，且同类问题反复占用数据人力。

## 2. 目标用户

运营、销售、管理层（非技术角色）——**会提问，不会写 SQL**。

## 3. 核心场景（3 个典型问句，均为实测通过）

| 问句 | 返回 |
|------|------|
| TikTok上个月卖了多少钱 | **1,073,966.76 元**（大数字 + SQL 展示） |
| 各渠道销售额对比 | Amazon 1,063万 > TikTok 638万 > DTC 483万 > Store 206万，柱状图 + 明细表 |
| 各品类销售额对比 | 四品类对比图（Accessories / Plush / Action Figure / Blind Box） |

## 4. 产品方案

```
中文提问 ──► LLM 生成 SQL（注入表结构 + 字段映射 + 时间锚点）
              │
              ├─► 字段校正：问题含"品类/渠道"时反向校验 GROUP BY 字段
              │
              ├─► 只读执行：仅放行 SELECT，SQLite 查询
              │
              └─► ECharts 图表 + 明细表格（单值结果显示大数字）
                     ▲
LLM 不可用（断网/无Key/超时）──► 本地规则兜底（关键词模板，<0.1s）
```

技术栈：Flask + SQLite + 智谱 glm-4-flash（OpenAI SDK 兼容协议）+ 原生 HTML/ECharts。

## 5. 价值

- **降低查询门槛**：自然语言即查询，非技术用户零学习成本；
- **缩短取数时间**：秒级响应（实测 LLM 路径平均 ≈2.7s，兜底路径 <0.1s），从"小时/天"级降到"秒"级；
- **可复用**：链路与数据源解耦，换数据源只需替换 schema 描述与数据文件，产品形态可直接平移到订单库、流量库等其他场景。

## 6. 关键设计决策

| 决策 | 理由 |
|------|------|
| 为什么用 SQLite | 单文件零部署，导入脚本 10 行即可跑通；当前量级（半年 2,880 行聚合数据）完全够用；读多写少场景无并发压力。数据量上来后平移 MySQL，SQL 几乎不用改。 |
| 为什么加规则兜底 | LLM 是外部依赖，会挂（断网/欠费/超时）。高频核心问句用关键词规则可 100% 稳定覆盖且耗时 <0.1s，保证"P0 场景永远有答案"。实测断 Key 状态下核心问句结果与真值一致。 |
| 为什么做字段混淆校正 | 实测发现 LLM 偶发把"品类"问题写成 GROUP BY channel——SQL 语法合法、**不报错但结果完全错误**，静默错误比报错更危险。用问题关键词反向校正仅 10 行代码，收益极高。 |
| 为什么注入时间锚点 | "上个月"依赖当前日期，而数据截止 2026-06-29；若让模型按真实日期推算会查空。把数据末日与映射规则（"上个月"= 2026-05-01~05-31）写进 prompt，实测所有时间类问句全部命中。 |

## 7. 效果摘要（详见测试记录）

- 15 条测试问句，LLM 路径准确率 **13/15（86.7%）**，P0 核心场景 100% 通过；
- 2 条失败均为派生指标/歧义词类（"转化率""流量最高"），已定位根因并列入改进项；
- 断 Key 兜底路径 7 问中 5 问可用（4 条与真值完全一致），暴露 2 条规则盲区，同为改进项。
